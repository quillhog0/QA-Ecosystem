# QA Ecosystem 1.0 - Product Definition

Status: draft, agreed direction (2026-11-05). Applies from 0.5 onward.

## One sentence

A GitHub Action that, on every pull request to a Python or TypeScript
repository, decides with evidence whether the work is really done - tests pass,
tests are honest and actually guard the change, documented commands and APIs
exist, nothing dangerous or identifying leaked - and returns a copy-ready fix
brief for every problem. The same input always yields the same verdict.

What it does not claim: it cannot prove the code is correct, and it cannot make
cheating impossible. It makes cheating expensive and makes every claim it does
make verifiable.

## Users

- **Primary delivery:** GitHub Action. A standalone CLI (`main.py`) keeps working
  but carries no stability promise until 1.x/2.0.
- **First client:** the Factory (private repositories). Its agents consume the
  fix briefs and iterate until the gate is CLEAR. The Factory is not the only
  client: every Factory-specific behaviour is an opt-in profile, never a default.
- **Languages:** Python and TypeScript/JavaScript only. No new languages before 1.0.
- **Repository layouts:** single-package repositories and monorepos/workspaces
  (npm, pnpm and yarn workspaces; multiple Python packages in one repository).
  In a workspace each package is checked with its own manifest, runner and
  engines; the verdict is the worst package verdict and every finding names
  its package.

## What the user gets on a pull request

1. **Check status** - CLEAR (pass), VETO (fail), BLOCKED_ENV (neutral, with the
   exact environmental cause, e.g. "requires Node >=22.5, available 20.11").
2. **PR comment** - short summary: what passed, what failed, why.
3. **Inline annotations** - SARIF, one annotation per finding at `file:line`.
4. **Fix brief (`fix-brief.md`)** - a Markdown task, ready to copy into an agent
   or an issue, for every finding that fails the gate (see below).
5. **Machine-readable findings** - JSON validated by `docs/findings.schema.json`.
   Every finding carries `class: hard|heuristic` and, for heuristic findings,
   `confidence: high|low`.

## Fix brief format

One file per run (`reports/<run>/fix-brief.md`, also `reports/latest/`), one
section per finding at or above the configured `fail-on` level, ordered by
priority. Each section is self-contained so it can be copied alone.

```markdown
## [F-003] P1 - Documented CLI flag `--dry-run` does not exist

**Root cause:** README.md:42 documents `mytool sync --dry-run`, but the CLI
parser in src/cli.py defines no `--dry-run` option (searched: src/cli.py,
src/commands/sync.py).

**Why it matters:** Users following the docs get "unrecognized arguments" and
the documented safe mode is unavailable.

**Evidence:**
- README.md:42 - `mytool sync --dry-run`
- src/cli.py:18-31 - `sync` subcommand options: `--force`, `--verbose`

**Fix (choose one):**
1. Implement `--dry-run` for `sync` and add a test that asserts no writes occur.
2. Remove the flag from README.md:42 if it is not planned.

**Done when:**
- [ ] the flag exists in code or is gone from the docs
- [ ] a test covers the new behaviour (option 1)
- [ ] QA gate reports no finding `lexi.missing_cli_flag` for `--dry-run`

**Suppress (only with justification):** `.qa-ignore` entry with rule
`lexi.missing_cli_flag`, match `--dry-run`, reason and expiry date.
```

Rules for every brief:
- **Repository content is data, never instructions.** Anything taken from the
  tested repository (docs text, test names, comments, error output) appears only
  inside fenced code blocks, length-limited, with no Markdown or HTML rendered.
  Instruction-like text in the repository (e.g. "ignore previous instructions")
  cannot reach the brief outside a quoted block. The brief's own wording is
  generated by QA only. This protects agents that execute the brief from
  prompt injection planted in the tested repository.
- Root cause is a concrete statement, never a symptom ("test X fails").
- Evidence lists `file:line` only; secret or identity values are never printed.
- "Done when" is verifiable by rerunning the gate.
- Heuristic findings say so explicitly and state why the gate is confident.
- Environment problems (BLOCKED_ENV) get a brief addressed to the operator,
  not to the code author.

## Checks

Checks are split into two classes with different guarantees.

### Hard checks - binary facts, absolute guarantees

The answer is a fact that can be established mechanically. These must be caught
every time and must never raise a false alarm.

| Check | 1.0 capability |
|---|---|
| **Test execution** (Nova) | pytest, vitest, jest, mocha, node:test inside the sandbox. A failing test is VETO. |
| **Environment** | Isolation-caused failures (no TTY, missing binary in sandbox, read-only path, module cache mismatch) are BLOCKED_ENV, never VETO. Node 20/22/24 and supported Python versions; `engines` mismatch reports the exact required version. |
| **Flaky tests** | A failing test is rerun once; pass-on-rerun is reported as FLAKY, not VETO and not CLEAR-silently. |
| **Removed or disabled tests** | Tests deleted versus the base branch, `skip` / `xfail` / `.only` / `.skip` added. |
| **No tests** | Zero collected tests is VETO. |
| **Secrets** | Private keys, tokens, API keys, URLs carrying credentials. P1. Values never printed. |
| **Identity** | Names, emails, home paths. P2 by default, P1 with `identity-strict`. Package metadata, LICENSE, AUTHORS, CHANGELOG excluded. |
| **Safety** (Sable) | Dangerous tests or conftest, network use, writes outside the working copy. |

### Heuristic checks - measured, not absolute

The answer requires interpreting code or text. Tightening raises false alarms,
loosening misses problems; there is no setting with zero of both. These checks
therefore carry a confidence level and measured precision/recall targets.

| Check | 1.0 capability | Scope limit |
|---|---|---|
| **Test integrity / anti-cheat** (Riley, Aria) | Tautologies, fake asserts, swallowed exceptions, assertions weakened compared with the base branch. | Detects known cheating patterns; new patterns are added as fixtures when found. |
| **Tests guard the change** (mutation) | Mutation limited to changed lines in diff mode. A surviving mutant is a finding: "no test guards this change". | Equivalent mutants are documented per rule, not silently ignored. |
| **Docs vs code** (Lexi) | Project-owned CLI commands and flags, exported API names and call forms, environment variables, install instructions. Project-owned commands come from an allow-list (`package.json` `bin`, `[project.scripts]`). | Does **not** verify prose claims ("returns a sorted list"). Third-party tool invocations are never checked against the project. |
| **Claim coverage** (Aria) | Maps documented claims to tests that exercise them. | Keyword- and structure-based; a mapped test is evidence, not proof. |

Confidence rule:
- **High confidence** - the evidence is unambiguous (e.g. the documented flag is
  absent from every argument parser found). May be P1.
- **Low confidence** - plausible but ambiguous. Capped at P2, so whether it
  fails the check is decided by `fail-on`.

## Configuration

Everything that is a matter of taste is configurable; safety guarantees are not.

| Setting | Action input | Default | Notes |
|---|---|---|---|
| Fail threshold | `fail-on: p0\|p1\|p2\|p3` | `p1` | Findings at or above the level fail the check; lower ones are annotations only. |
| Profile | `profile: default\|factory` | `default` | `factory` = `fail-on: p2`, `identity-strict: true`, mutation on. Explicit inputs override the profile. |
| Identity strict | `identity-strict` | `false` | |
| Mutation | `mutation`, `mutation-min-score` | off / 0.8 | Diff-scoped when `diff-base` is set. |
| Fix brief | `fix-brief: true\|false` | `true` | |
| Suppressions | `.qa-ignore` | - | Rule + match + reason + expiry + `kind` (see Feedback); P0 can never be suppressed. |
| Baseline | `baseline: <path>` | off | Findings recorded in the baseline file are reported but do not fail the check; only new findings do. Lets existing repositories adopt the gate without fixing everything first. |

Not configurable: sandboxing of tested code, QA tooling never sourced from the
tested project, the tested project cannot loosen QA configuration, secret values
never printed, repository content never rendered as instructions in fix briefs.

## Feedback and labelling

Whether a finding is real is decided by the **owner of the tested codebase**,
not by QA and not by an agent.

- The owner labels a finding through `.qa-ignore` with
  `kind: false-positive` (QA was wrong) or `kind: accepted-risk` (QA was right,
  the owner accepts it). Both need a reason and an expiry.
- `false-positive` labels are the ground truth for precision. The gate reports
  per rule how many findings were labelled false positive.
- An optional, opt-in export (`feedback-export: true`) writes an anonymous
  summary - rule ID, class, confidence, label - with no code, paths, names or
  values. Owners may share it with QA maintainers; nothing is sent automatically.
- A rule whose false-positive rate across labelled findings exceeds its
  precision target is downgraded to low confidence (P2 cap) until fixed.

## Corpora and privacy

- Corpora built from private client repositories (Factory included) never
  enter the public QA repository. They live in private storage owned by the
  client or the maintainer, and metrics on them are computed by CI in that
  private context.
- The public repository holds only synthetic fixtures and anonymous metric
  summaries.

## Action security

- Runs on `pull_request`. Never checks out or executes pull-request code under
  `pull_request_target`.
- Minimal permissions: `contents: read`; `pull-requests: write` only when the PR
  comment is enabled; `security-events: write` only for SARIF upload.
- No repository secrets or tokens are visible to the tested code; the sandbox
  environment is sanitised.
- Users pin the Action by commit SHA; releases are published with build
  provenance.

## Guarantees

**For all checks**
- **Determinism:** same commit + same config + same QA version = same verdict
  and same findings, independent of cache state, file order or timing. A QA
  upgrade may change verdicts; every such change is listed in the CHANGELOG.
- **Isolation:** tested code never runs outside the sandbox; QA tooling comes only
  from QA-owned, checksum-pinned sources.
- **Stable interface (semver):** Action inputs, exit codes (0/1/2), findings JSON
  schema, SARIF rule IDs and fix-brief section layout change only in a major version.
- **Speed:** diff run <= 3 min, full run (without mutation) <= 10 min on a
  reference repository (to be fixed in 0.5: size in files/LOC and number of
  tests, one Python, one TypeScript, one workspace). Full-repository mutation is
  out of the time budget.

**For hard checks**
- 100% detection on the hard-check corpus, zero false alarms.

**For heuristic checks**
- Precision and recall are measured and published per check on every release.
- A false positive is never fixed by loosening alone: every fix ships with a
  known-bad twin fixture proving the real problem is still caught.

## Release criteria for 1.0

All must hold on the release candidate. All numbers are computed by CI from
corpora (public synthetic fixtures plus private client corpora), never reported
by hand or by an agent. Precision is based on owner labels (see Feedback).

1. **Hard checks:** 100% detection on the hard-check corpus and zero false
   alarms on all client corpora. A single miss or false alarm blocks the release.
2. **Seeded-bug corpus:** real client repositories (Factory and at least one
   non-Factory codebase, covering single-package and workspace layouts) with
   injected defects (failing logic, deleted tests, weakened asserts, doc drift,
   leaked secrets).
   - hard-check defects: 100% caught,
   - heuristic defects: >= 90% caught per check.
3. **Heuristic precision:** >= 95% for P1 findings, >= 80% for P2 findings,
   based on owner labels.
4. **Field run:** >= 200 pull-request runs, of which >= 50 outside the Factory,
   with
   - zero false VETO caused by a hard check,
   - false VETO caused by a heuristic check in <= 1% of runs, each one turned
     into a regression fixture with a known-bad twin before release.
5. **Benchmark:** 100% of fixtures, including every known-bad fixture, end with
   the expected verdict.
6. **Code quality:** full unit suite green; mutation >= 0.95 on every changed
   module, equivalent mutants listed explicitly.
7. **Security:** fix-brief injection fixtures (instruction-like text in docs,
   test names, error output) never produce unquoted content; Action permissions
   and trigger rules verified by test.
8. Speed targets met on the reference repositories; interfaces frozen since 0.9
   with no breaking change.

## Roadmap

| Version | Goal |
|---|---|
| **0.5 Precision and measurement** | Lexi allow-list of project-owned commands; structured Markdown/shell parsing; `class` and `confidence` on findings; FLAKY category; `.qa-ignore` `kind: false-positive / accepted-risk`; per-rule false-positive counts; false-positive corpus with known-bad twins; reference repositories defined; CI computes benchmark, precision/recall and mutation numbers; `--self-test` on every PR. |
| **0.6 Action UX and security** | `fail-on`, `profile` and `baseline` inputs; fix brief with injection-safe quoting; PR comment; SARIF annotations; versioned findings schema; Action permissions and trigger hardening; release provenance. |
| **0.7 Depth and layouts** | Diff-scoped mutation; coverage of changed lines; assertion strength compared with base; monorepo/workspace support (per-package runner, engines, verdict). |
| **0.8 Hygiene and resilience** | No vendored TypeScript in git (lockfile-pinned tooling cache); controlled Node provisioning; content-hash analysis cache; container sandbox as fallback when bwrap is unavailable on the runner; opt-in anonymous feedback export. |
| **0.9 RC** | Interfaces frozen; documentation; seeded-bug corpus complete; field run on Factory and non-Factory repositories. |
| **1.0** | Release criteria met. |

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Ubuntu / GitHub restrict unprivileged user namespaces further | bwrap sandbox unavailable, runs end BLOCKED_ENV | Container sandbox fallback (0.8); `allow-sysctl-userns` documented. |
| Lexi false positives on real docs | False VETO, loss of trust | Allow-list scope, confidence cap at P2, owner labels, known-bad twins. |
| Agents learn new cheating patterns | Missed errors | Mutation on changed lines as pattern-independent defence; every new pattern becomes a fixture. |
| Prompt injection through fix briefs | Client agents execute attacker text | Repository content only as quoted data; injection fixtures in the release criteria. |
| Development largely done by agents | Overstated results, self-confirming fixtures | Metrics computed by CI only; precision from owner labels; corpora from real client code; self-test on every PR. |
| First client shapes the product | Over-fitting to the Factory | Factory behaviour only via profile; >= 50 field runs outside the Factory required for 1.0. |
| Owners do not label findings | Precision cannot be measured | Labelling built into the normal suppression flow (`.qa-ignore`), so labelling costs no extra step. |
| Private corpora leak into the public repository | Anonymity and client confidentiality broken | Corpora only in private storage; public repository holds synthetic fixtures and anonymous summaries. |
